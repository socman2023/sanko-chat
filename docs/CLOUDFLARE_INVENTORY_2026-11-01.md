# Шаг 4.1. Подтверждённая инфраструктура Cloudflare

**Дата фиксации:** 1 ноября 2026 года  
**Статус:** **ЗАВЕРШЁН.** Конфигурация действующего чата Олешки подтверждена владельцем проекта; bindings также видны на предоставленном скриншоте Cloudflare Dashboard. Дополнительных скриншотов не требуется. Рабочие ресурсы Олешки не изменялись.

## 1. Исходные версии и лимиты

- **Рабочий Worker Олешки:** `oleshka-chat-api`, **v3.9.1**. Версия прямо подтверждена владельцем проекта 1 ноября; в предыдущей истории работы после развёртывания проверялся ответ с `"version":"3.9.1"`.
- **Лимиты Олешки:** **500 запросов в сутки / 15 000 в месяц / 100 с одного IP за сутки**. Владелец подтвердил именно эти текущие значения.
- **Лимиты нового Worker Санко:** **такие же 500 / 15 000 / 100**; настроить при создании Worker.
- Файлы `oleshka-worker-v3.8.0-diary-staging.js` и более ранние — **архивные**, не действующий исходник. Не использовать их как основную версию и не переносить оттуда настройки, модели или ограничения без сверки с v3.9.1.
- Старые значения 60 / 700 / 20 отменены и более не должны появляться в планах внедрения.

## 2. Подтверждённые ресурсы в Cloudflare

Скриншот **Workers & Pages → oleshka-chat-api → Settings** показывает действующие production bindings:

| Тип | Binding | Ресурс |
|---|---|---|
| Workers AI | `AI` | Workers AI Catalog |
| KV namespace | `CURRENT_CONTEXT` | `heroes-chat-current` |
| D1 database | `GUARD_DB` | `heroes-chat-guard` |
| Vectorize index | `KNOWLEDGE` | `heroes-knowledge` |

Существование и неизменность конфигурации подтвердил владелец проекта. **Не требовать повторного подтверждения имен bindings.**

В разделе Runtime variables and secrets видны существующие имена `ADMIN_UPDATE_TOKEN`, `GEMINI_API_KEY`, `VK_APP_ID`, `VK_APP_SECRET`, `VK_CHRONICLE_GROUP_ID`, `VK_OLESHKA_USER_ID`, `VK_SERVICE_TOKEN`. Значения секретов не раскрывались и **не нужны** для подготовки проекта Санко.

**Расположение Vectorize в текущей панели Cloudflare: раздел AI, а не Storage & Databases.** В предыдущей инструкции навигация была указана неправильно.

## 3. Принятое решение для Санко

Создать отдельный Worker `sanko-chat-api` и отдельную D1 для истории и лимитов Санко.

Подключить существующие **общие** ресурсы:
- Workers AI `AI`;
- Vectorize `KNOWLEDGE` → `heroes-knowledge`; выборка строго по `character in ["shared","sanko"]`;
- KV `CURRENT_CONTEXT` → `heroes-chat-current`; персональные ключи Санко имеют префикс `sanko:`, без изменения ключей `oleshka:`.

Для D1 нового Worker использовать собственный binding `GUARD_DB` на отдельную базу, чтобы обеспечить независимые журналы и счётчики. Лимиты 500/15 000/100 применить только к обращениям Санко. Отдельные лимиты двух Workers **не равны** общему денежному лимиту Gemini: контроль совокупных расходов требует дополнительной настройки на стороне провайдера или отдельного механизма учёта.

Системная инструкция Санко и персональный корпус знаний берутся из согласуемого пакета v0.2; сами личные материалы не становятся общими данными Олешки.

## 4. Проверки при разработке, а не повторный аудит Олешки

При создании **нового** Worker Санко проверить:
1. Доступность общих bindings `AI`, `KNOWLEDGE`, `CURRENT_CONTEXT` **со стороны Санко**.
2. Создание **новой** D1 и корректную запись счётчиков Санко.
3. Наличие metadata-фильтра `character` в общем Vectorize; отсутствие утечки `oleshka`-фрагментов.
4. Установку лимитов 500/15 000/100 и изоляцию расхода одного чата от другого.
5. Контрольный ответ именно Санко и сохранение истории только Санко.

Эти проверки относятся к **создаваемой системе Санко**. Они не означают, что необходимо перепроверять или менять работоспособный чат Олешки.
