## 4. Режим общих знаний и персональных фильтров

Сохранённый Worker Олешки использует:
```js
const CHARACTER_FILTER = { character: { $in: ["shared", "oleshka"] } };
```
Для нового Worker Санко требуется фильтр `["shared", "sanko"]`. Однако фильтра недостаточно без **проверки самих метаданных**: записи `shared` не должны выдавать чужие личные мысли, а индексирование `sanko` должно быть отдельным. Подключение к тому же Vectorize не даёт Санко права всезнания.

KV Олешки использует префиксы `oleshka:current:v1`, `oleshka:recent:v1`, `oleshka:day:` и `oleshka:vk:*`. Санко может применять `sanko:*` в том же namespace, но общие ключи и личные события не смешивать.

## 5. Хранение диалогов, квоты, секреты

Сохранённый код использует D1-таблицы `chat_admissions`, `chat_turns`, `vk_manual_roles`, `vk_relation_cache`, `oleshka_vk_diary`. **Наличие каждой таблицы в живой D1 не проверено**.

- `chat_turns` имеет поле `character` в операциях сохранения. Это полезно, но не означает независимые квоты: операции с `chat_admissions` в v3.8 не фильтруются по персонажу.
- Кодовый верхний предел v3.8: 500 допущенных запросов в день, 15000 в месяц и 100 с IP за день. Конфигурационные переменные могут **понизить** их. В прежней настройке фигурировали 60/день, 700/месяц, 20/IP/день, но **текущие значения не проверены**.
- Учитываются **допущенные запросы**, а не стоимость Gemini в валюте.
- История разговоров в браузере Олешки — до 80 сообщений; контекст отправляемого запроса — до 12. Серверный код v3.8 сохраняет диалоги с целевым сроком хранения 30 дней.
- Для Санко рекомендуется **отдельная D1** для диалогов и ограничений, чтобы не менять работающую схему Олешки; общесистемный бюджет для двух Workers ограничивать дополнительно.
- Секреты Gemini и VK нельзя переносить в GitHub, логировать или копировать в клиентский JS. Для Санко понадобится самостоятельный VK App ID/secret после регистрации приложения.

## 6. Версионность

В исходных файлах доступна версия Worker `v3.8.0`; в истории разработки 1 ноября упоминается `v3.9.1`. **Нельзя выдавать `v3.9.1` за подтверждённый deployed source**, пока его версия не прочитана непосредственно в Cloudflare. Перечень моделей Gemini из `v3.8.0` не считать актуальным до сверки.

## 7. Точная проверка в Cloudflare (только просмотр)

В аккаунте Cloudflare открыть:
1. **Workers & Pages → `oleshka-chat-api` → Overview / Deployments:** текущая версия и её время.
2. **Settings → Bindings:** `AI`, `KNOWLEDGE`, `CURRENT_CONTEXT`, `GUARD_DB`.
3. **Settings → Variables and Secrets:** только **имена** переменных; для лимитов — видимые не секретные значения. Никаких значений секретов.
4. **Triggers:** расписание Cron.
5. **Storage & Databases → Vectorize → `heroes-knowledge`:** dimensions, total vectors, metadata indexes, namespace.
6. **Storage & Databases → KV → `heroes-chat-current`:** namespace ID и только имена префиксов (не публиковать содержание личных контекстов).
7. **Storage & Databases → D1 → `heroes-chat-guard`:** database ID и схема/список таблиц (без чтения чужих сообщений).

**Без этого шага live-конфигурация остаётся не подтверждённой.** Не требуется передавать API-токен в чат. Проверку можно произвести через облачный браузер Work или предоставить скриншоты без секретов.

## 8. Решение для этапа 4.2

Заранее установленный безопасный контур:
- новый Worker **`sanko-chat-api`**;
- отдельный D1 Санко;
- общие Cloudflare Workers AI и `heroes-knowledge`, фильтр персонажа `shared|sanko`;
- при подтверждении доступности — общий KV namespace `heroes-chat-current` с исключительно `sanko:*` ключами;
- независимые `GEMINI_API_KEY` binding и ограничения модели без раскрытия секрета;
- отсутствие каких-либо изменений действующего Worker Олешки.

**Граница завершения шага 4.1:** инвентаризация кода выполнена, live-сверка не выполнена. Исходники нового Worker готовить можно; привязывать ресурсы и запускать — только после подтверждения фактических binding-имен.

## 9. Ограничения Cloudflare (публичная документация, не конфигурация аккаунта)

По документации Cloudflare D1 от 30 октября 2026 года, на бесплатном плане разрешено **до 10 баз D1 на аккаунт**, с ограничением **500 МБ на базу и 5 ГБ суммарно**. Поэтому создание отдельной D1 для Санко технически укладывается в ограничения Free **только если свободен хотя бы один слот**; фактическое число баз в аккаунте не проверено. Источник: https://developers.cloudflare.com/d1/platform/limits/

Cloudflare подтверждает поддержку фильтра Vectorize вида `{character:{$in:['shared','sanko']}}`, **если metadata index `character` создан и данные индексированы корректно**. Уже загруженные векторы могли быть добавлены до создания индекса, поэтому проверить наличие индекса недостаточно: нужны тестовые запросы и сверка метаданных. Источник: https://developers.cloudflare.com/vectorize/reference/metadata-filtering/

Один KV namespace можно привязать к Worker по его ID под локальным именем binding; это не превращает все ключи в отдельные базы. Источник: https://developers.cloudflare.com/kv/concepts/kv-bindings/
