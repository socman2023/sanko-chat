# Один дневник для Олешки и Санко

**Дата:** 2 ноября 2026 года  
**Статус:** чтение дневника реализовано в коде Worker Санко, **не активировано в Cloudflare**, пока не привязан существующий D1 `heroes-chat-guard` под новым именем binding `DIARY_DB`. Рабочий Worker Олешки 3.9.1 и его 3-часовой Cron НЕ меняются.

## Почему нельзя полагаться только на KV и Vectorize

- Worker Олешки 3.9.1 автоматически синхронизирует опубликованные записи ВК каждые 3 часа через Cron.
- Первичные тексты и публикационные даты находятся в таблице `oleshka_vk_diary` его D1 `heroes-chat-guard`.
- Фрагменты публикаций также попадают в общий индекс `heroes-knowledge`, но общий поиск без отдельной проверки не должен снимать запрет Санко на доступ к личным материалам Олешки. Текущий фильтр RAG `shared/sanko` сохраняется.
- KV `oleshka:recent:v1` из более ранней архитектуры не подтверждён как автоматически обновляемый Cron 3.9.1. Не подменять настоящую синхронизацию старыми KV-записями.

## Реализация

В `worker/src/index.js` есть `loadPublishedDiary(env,scope)`, которая читает `DIARY_DB` с **SELECT**, выбирая публикации ВК `owner_id=850667816`, исключая `category IN ('excluded','rejected')`. При обычном разговоре используются последние 10 публикаций (не более 9000 символов в сумме); при вопросе об определённой дате — до 12 публикаций за дату публикации. **Дата публикации не всегда является датой описываемого события**, об этом прямо предупреждается Gemini.

- Подключение только читает опубликованные тексты Олешки. Оно не выдаёт личный профиль, KV-контекст, скрытые инструкции, частные переписки или журнал ограничений Олешки.
- Политика речи: «Олешка писал», «в дневнике прочёл», если Санко не видел события. Даже истинные сведения из дневника не превращаются автоматически в собственную память.
- Отдельные чаты, D1 `heroes-chat-sanko`, лимиты 500 / 15 000 / 100 и ключи `sanko:*` остаются неизменными.
- На Cloudflare D1 binding нет технического ограничения «read-only» как у роли SQL; **только наш код** делает SELECT. Не добавлять административных SQL-операций на `DIARY_DB`.

## Для окончательного подключения

Требуется **только Database ID уже существующей `heroes-chat-guard`**, не ID базы Санко.

После получения ID добавить в корневой `wrangler.toml`:

```toml
[[d1_databases]]
binding = "DIARY_DB"
database_name = "heroes-chat-guard"
database_id = "<ФАКТИЧЕСКИЙ_UUID_ИЗ_CLOUDFLARE>"
```

Коммит в репозиторий `socman2023/sanko-chat` автоматически развернёт обновление **только Worker Санко**. Никакой новой базы, копии записей, второго Cron, редактирования `oleshka-chat-api` и создания таблиц в `heroes-chat-guard` не требуется.

## Проверка после привязки

1. `GET /health` у Санко: `character:"sanko"`, `configured:true`, `diaryConnected:true`.
2. Спросить «Что Олешка написал в дневнике вчера?» — ответ должен явно исходить из прочитанного, без присвоения чужих впечатлений.
3. В ответе API поле `knowledge.diaryPosts` должно показывать число использованных публикаций.
4. Проверить вопрос о недавно опубликованной записи после ближайшего штатного Cron Олешки; не запускать вручную новые импорты и не менять Cron.
5. На уровне кода и тестов проверить, что `DIARY_DB` используется **только** для `SELECT`.

**До получения ID** Worker Санко остаётся работоспособным с личными знаниями и общим RAG, но **не может честно утверждать, что получает свежий дневник Олешки через D1**. Этот статус отражён в `GET /health`: `diaryConnected:false`.
